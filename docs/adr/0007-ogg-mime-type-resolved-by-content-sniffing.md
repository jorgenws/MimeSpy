# Ogg's primary mime type is resolved by sniffing the codec, not by alias count

A single row in `file_signatures.csv` covers every Ogg file (`oga|ogg|ogv|ogx`), and those extensions resolve to three different mime types in `mime.types`: `audio/ogg`, `video/ogg`, and `application/ogg`. [ADR 0004](0004-primary-mimetype-by-extension-alias-count.md)'s alias-count heuristic picks `audio/ogg` as `PrimaryMimeType` for all of them, since `ogg` and `oga` both resolve to it - but that's wrong whenever the file actually holds video (Theora, OGM, Skeleton) or something that's neither (Kate). This isn't the same shape of problem [ADR 0001](0001-ambiguous-matches-returned-as-ties.md) and [ADR 0002](0002-zip-disambiguation-reads-only-supplied-bytes.md) solve: those narrow a tie between *multiple signature rows* sharing one header; Ogg is a single row whose own mime type list is ambiguous, and `ResolveMimeTypes` only has extensions to go on at table-load time, not file content.

We decided to resolve it the way `file(1)`/libmagic does: peek at the codec identification packet immediately after the first page's header (byte offset 28 - see `Resources/ogg_codec_identifiers.csv` for the exact patterns and their source) and use it to override `PrimaryMimeType` at `Spy` time. `OggContainerSniffer` runs unconditionally (not gated on `results.Count > 1` like `ZipContainerSniffer`) and only touches a result whose `MimeTypes` already contains the sniffed value, so it can't affect an unrelated match. When those bytes aren't available - a short buffer, or a codec not in the table - it falls back to today's alias-count answer rather than guessing, consistent with how ZIP disambiguation falls back to the tied list.
