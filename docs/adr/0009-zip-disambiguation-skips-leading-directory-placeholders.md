# ZIP container disambiguation skips leading zero-length directory entries

`ZipContainerSniffer` narrows a ZIP-based match by the name of the archive's first entry (see docs/adr/0002). Real integration-test fixtures pulled from Apache Tika's test corpus showed this is too literal: a genuine docx from Word had `_rels/` as its first entry rather than `[Content_Types].xml`, and a genuine jar had `META-INF/` rather than `META-INF/MANIFEST.MF` - both common, spec-legal directory placeholder entries that real writers put ahead of the file that actually matters. Checking only the literal first entry meant these real files never narrowed, always falling back to the full tied list. We decided to walk past any leading entry whose name ends in `/` and whose compressed size is 0 before checking the name, still reading only forward from the bytes already supplied (never seeking to the central directory, per docs/adr/0002) and still returning `null` the moment a non-placeholder entry's name doesn't match one of the known patterns.
