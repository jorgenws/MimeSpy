# Mime-type table sourced from Apache's mime.types, not mime-db

[jshttp/mime-db](https://github.com/jshttp/mime-db) aggregates registrations from IANA, Apache, and nginx, and it can legitimately list more than one mime type for the same extension - e.g. `mp4` resolves to both `application/mp4` and `video/mp4`, both currently registered with IANA. Resolving an extension then depends on the alias-count heuristic in [ADR 0004](0004-primary-mimetype-by-extension-alias-count.md) to guess which one is "canonical," which is a guess, not a fact. We decided to source `Resources/mime.types` from [Apache httpd's mime.types](https://svn.apache.org/repos/asf/httpd/httpd/trunk/docs/conf/mime.types) instead: it's a single curated list with one mime type per extension for nearly every entry, so resolution is deterministic rather than heuristic. The cost is coverage - about 240 of mime-db's ~1000 extension-bearing entries (mostly niche IANA registrations and vendor `vnd.*`/proprietary types) aren't in Apache's list, though only ~23 of those extensions are ones `Resources/file_signatures.csv` can actually reach, and those were judged low-value. Apache's list isn't perfectly unambiguous either (`.wmz` and `.sub` each still resolve to two mime types), so ADR 0004's tie-break rule stays in place, just rarely exercised now. nginx's mime.types was considered as a combined secondary source to recover some of that lost coverage, but it disagrees with Apache's list on 13 extensions it also lists (including `.xml` and `.js`), which would have reintroduced the exact ambiguity this change is meant to remove - so it was left out.
